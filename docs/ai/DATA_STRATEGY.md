# 데이터 구조 전략 — 법령 원문을 한 원본에서

정리일: 2026-11-07. **계획 문서이며 구현 완료 기록이 아니다.** 측정 수치의 원본은 [CURRENT_STATUS.md](CURRENT_STATUS.md)
"법령 데이터 감사 — 2026-11-07", 전체 순서는 [ROADMAP.md](ROADMAP.md), 결정은 [DECISIONS.md](DECISIONS.md) ADR-081이다.

## 문제

같은 법령 원문이 두 곳에 있다. 현행 표(`law_articles`, 법령 API로 한 번 채움)와 과거 법령 보관소(`law_history`, 시행본마다 공식 XML과 해시).
둘을 맞추는 장치가 없어서 현행 표는

- 파서가 자른 조문을 그대로 두었다(정의 조항이 첫 문장만 남은 경우 포함). 기존 결손 탐지(`has_missing_items`)는 이런 행을 대부분 놓친다.
- 이미 시행 중인 새 시행본을 반영하지 못했다(조문 문구 변경, 새 조문).
- 읽을 때마다 보관소로 임시 복구(`source_recovery`)해 결함을 가려 왔다.

파생 데이터(항 조각·벡터)는 절반만 어떤 원문·입력·모델에서 만들었는지 기록하고, 해석례는 조문 표에 다른 뜻의 칸으로 들어 있으며(법령명 칸에 인용 법령,
조문 번호 칸에 사건 번호), 조문 사이 관계는 실행 시점 정규식과 꺼지면 조용히 빠지는 Neo4j에만 있다.

보관소는 상태가 좋다: 공식 XML·해시, 개명된 법령의 같은 ID(상속세법 → 상속세및증여세법), 조문별 시행일, 부칙, 이미 수집된 최신 시행본.
한 번 공포된 법령(MST)이 단계적으로 시행되면 시행일마다 버전이 따로 있으므로 **버전은 (MST, 시행일)로 식별한다.**

## 원칙 (이 프로젝트의 시행착오에서)

1. **원본은 하나**: 공식 XML 보관소가 원본이고, 현행 조문·항 조각·벡터·관계·검색 문서는 그로부터 다시 만들 수 있는 파생물이다. 읽을 때 고치지 않는다(ADR-069).
2. **파생물마다 출처표**: 원문 해시, 입력 글 해시, 추출기·파서 버전, 모델 키(보관소 `search_chunks.model_key`처럼).
3. **나란히 만들고 비교한 뒤 전환**: 그림자 표 → 차이 보고서 → 검색 평가셋·공식 회답 정답셋 → 설정으로 전환, 옛것은 되돌리기용으로 둔다.
4. **Postgres가 기준**, Neo4j는 관계 표의 투영(ADR-060의 조용한 누락을 반복하지 않는다).
5. **종류가 다른 자료는 다른 표**: 조문·해석례·(앞으로) 예규.
6. **새 장비·모델 없음**: 재임베딩은 로컬 Ollama.

## 목표 구조

```
[원본]   law_history.snapshots(공식 XML·해시) + 해석례 원본(API 응답·해시)
            │ 결정적 파싱(파서 버전 기록)
[정규]   laws(법령 ID·정식명·별칭·상위법) → versions(MST, 시행일) → provisions(조·항·호, 조문별 시행일, 삭제)
         interpretations(사건번호·회신일·질의·회답·이유)      supplements(부칙)
            │ 결정적 추출(추출기 버전·근거 구간)
[관계]   provision_relations: 위임(법→시행령→시행규칙)·인용·정의·해석례→적용 조항
            │ "오늘 시행 중"으로 생성 + 출처표
[검색용] 현행 조문 보기 · 항 조각 · 벡터(입력 해시·모델 키) · BM25 문서        ← 서비스가 읽는 곳
            │
[평가]   정답셋은 (법령 ID, 버전)으로 정답을 고정
```

## 단계

| 단계 | 내용 | 확인 | 상태 |
|---|---|---|---|
| P0 감사 | `scripts/audit_law_data.py`: 보관소 대비 교체 후보·뒤처진 법령·없는 조문·같은 시행본 문구 차이·출처표 누락. 읽기만 한다 | 수집할 때마다 실행, 기준값을 CURRENT_STATUS에 | 구현 |
| P1 긴급 정정 | 현행 표의 잘린 조문(같은 시행본)과 문구가 바뀐 조문(오늘 시행 중인 시행본)을 보관소 XML을 같은 파서로 다시 읽어 교체하고 그 행만 재임베딩. `scripts/repair_law_indexes.py --source archive`(미리보기 → 적용 → 되돌리기, 행마다 백업) | 계획 목록 확인 후 적용, 검색 평가셋 전후 비교 | 적용(2026-11-07, 251/252, 1개는 P2로) |
| P2 단일 원본 전환 | 현행 조문 보기를 보관소의 "오늘 시행 중" 버전으로 생성(그림자 표). 행마다 법령 ID·버전·MST를 기록하고 형식 통일, 새 조문 추가. 입력이 바뀐 행은 `embedding_v2`에 재임베딩. 새 시행본이 시행되면 자동 재생성 | 차이 보고서 → 검색 평가셋 → 정답셋 → 설정 전환 | 적용(2026-11-07, 제자리 방식: `scripts/rebuild_current_laws.py`). 정답셋 확인·출처표 보완·자동 재생성은 남음 |
| P3 관계 표 | 위임·인용·정의·해석례 관계를 Postgres 표로(근거 구간·원문 해시·추출기 버전). 위임 결합 정규식과 Neo4j를 이 표 기반으로. 연결 보류 인용 정리 | 위임 결합 결과가 같거나 나은지, 연결 보류 수 감소 | 계획(P2 뒤: 원본이 바뀌면 다시 만들어야 하므로) |
| P4 자료 종류 분리 | 해석례를 전용 표로(질의·회답·이유·인용 항). 검색은 종류별로, 정답셋은 이 표를 읽는다. 예규·질의회신은 정답셋 결과를 보고 같은 틀로 | 정답셋 재생성 결과 동일 | 계획 |
| P5 조문별 시행일·부칙 | 보관소의 조문시행일자·부칙으로 사건일 적용 판정(알려진 미해결: 부칙 적용례·경과조치) | 날짜가 있는 정답셋 문항 | 계획 |

P2를 그림자 표 대신 제자리에서 한 이유: 감사 결과 바뀌는 행이 버전 표시 4,534·글 139·현행 아님 8·추가 3개뿐이라, 전부 새로 만들면
2만여 개 벡터를 이유 없이 다시 만든다. 대신 단계마다 원래 값을 저장하고 내용 해시로 대조하며, 미리보기를 다시 돌려 변경 0을 확인했다.
교훈: 버전 표시를 바꾸면 그 날짜를 쓰는 다른 기능(사건일 판단)이 함께 바뀐다. 행에는 "가져온 버전"(`effective_date`)과 "이 문구가 시행된 날"
(`in_force_since`)을 따로 두고, 감사가 날짜별 판단 가능 조문 수를 매번 보고한다(2026-11-07, ADR-081 보완).
교훈: 비교 기준은 항상 **오늘 시행 중인 시행본**이다. 행에 적힌(뒤처졌을 수 있는) 버전과 비교하면 이미 새 글을 가진 행을 옛 글로 되돌릴 수 있다(법인세법 제90조).

하지 않는 것: 한 번에 전부 교체, API 재수집(원문은 보관소에 있다), 읽을 때 고치는 경로 추가, 새 DB 기술·GPU 모델.

검토 후 하지 않기로 한 것: 보관소 법령명 정규화 — 띄어쓰기만 다른 옛 이름(소득세법시행령/소득세법 시행령)이 이미 같은 법령 ID로 묶여 있고
조회가 법령 ID로 이뤄져 효과가 없다(2026-11-07 확인).

# 주요 설계 결정

## ADR-030 — 역사 본문 임베딩 공유와 조회 시점 인용 해석

- 원본 5,400 버전은 보존하고 조문/부칙 고유 본문 및 청크를 별도 색인한다. 모델 규격이 다르면 벡터를 혼용하지 않는다. 전체 백필은 독립 history-index profile worker로 실행한다.
- HistoryLaw/Version/Snapshot/Text/Name과 소속·관측 순서·명시적 MENTIONS를 추가한다. 기존 현행 그래프를 변경하지 않는다. 동일 ID 연결은 과거 계열 적용의 인증이 아니다.
- 역사 질문은 도구 선택 전에 별도 경로로 분리한다. 날짜/버전 불명확·동일 시행일 복수 후보·미수집·미임베딩은 유보하며 현행/웹 fallback을 금지한다.
- 인용 대상은 질문 기준일로 다시 버전을 조회하고 항/호/목·PG 원문 해시/인용 문구를 검증한다. 날짜순 최신 후보를 사건 적용 법령으로 확정하지 않는다.
- 구조화 답변 source ID와 원문 인용문을 검증하고 버전 링크를 코드로 생성한다. 현행 조문 뷰어로 재연결하지 않는다. 의미적 법률 정확도와 전체 검색 품질 검증은 별도다.

## ADR-029 — 과거 법령 수집기는 독립 opt-in 배치

- API 내부 docker exec 작업 대신 history profile 전용 worker. 채팅 재배포와 수집 수명을 분리한다.
- 트랜잭션/유일 키/DB advisory lock을 보존하며 pending만 재개한다. on-failure:3 제한 복구이며 PC/WSL 자체 부팅은 자동화하지 않는다.
- 상태 조회는 저장 status와 잠금/heartbeat 기반 observed_status를 분리한다. 오래된 heartbeat만으로 살아 있는 잠금을 해제하지 않는다.
- 전체 수집 범위 완료 뒤 읽기 전용 전체 무결성 검수와 공식 API 표본 대조를 실행하고 시각별 JSON 보고서를 보존한다. 법적 시점 적용 검수는 별도다.

## ADR-028 — 구법은 현행 검색과 분리된 시행일 버전 아카이브

- 기존 law_articles의 콘텐츠 해시/현행 플래그는 전체 법령 연혁 모델이 아니다. 이를 덮어쓰지 않고 PostgreSQL law_history에 공식 법령 ID와 (MST,시행일)별 버전을 저장한다.
- eflaw 목록의 LID/nw=1,2,3 전체 페이지와 본문 MST+efYd를 사용한다. 공포본만으로 단계 시행 원문을 대체하지 않는다. 원문 ID·시행일·공포일 대조 실패는 수집 실패다.
- 원문 해시+파서 버전으로 스냅샷을 추가 보존한다. 삭제 조문·표제·부칙은 생략하지 않는다. 인증 OC는 저장 전 정제한다.
- version_sequence는 시간순 관측 연결이며 법적 승계나 효력 종료일의 확정이 아니다. 부칙 적용·조문 이동/분할/통합은 별도 검수가 필요하다.
- 현재 수집 범위를 최초 실행 시 고정하고 실패·미수집과 완료를 분리한다. 기본 재실행은 미완료만, refresh는 명시적. 단일 worker lock, 제한 재시도, 연속 실패 중단을 사용한다.
- 구법 임베딩 및 Neo4j 투영·채팅 연결은 검증 후 후속 적용한다. 현재 요청의 수집만으로 현행 RAG를 전환하지 않는다.

## ADR-027 — 마지막 턴 수정은 원본 보존형 대화 복사

- 마지막 완료된 user/assistant 쌍만 수정·재생성한다. 마지막 메시지 ID로 오래된 화면의 요청을 거부하고 소유권 확인 후 이전 문맥만 새 대화로 복사한다.
- 기존 답변 삭제/덮어쓰기 없이 실패 시 원본 복귀가 가능하다. 사용자에게 별도 대화 생성 방식을 안내한다. 전체 분기 트리와 한 대화 내 버전 전환은 후속이다.
- 복사는 기존 JSON 메시지와 도구 결과를 보존하고 마지막 턴은 복사하지 않는다. 대화 읽기 순서는 chat_logs.id 기준이다. DB 스키마 변경은 없다.

## ADR-026 — Judge 증거는 문장 ID와 평가 항목별 정책으로 검증

- Judge는 보조 판정이며 인간 Adjudication/배포 gate를 변경하지 않는다. 원문 재작성 대신 A/R ID를 반환하고 코드는 원문을 복원한다.
- 법적 일반 기준은 원문 증거를 요구한다. 기존 승인 합성 사례 answer-insufficient-context의 행동 기준 3개에 한해 원문 발췌 강제를 해제한다. 다른 기준으로 자동 확장하지 않는다.
- support/omission/absence를 구분하고 omission은 fail, absence는 pass 및 전체 답변 ID 범위를 요구한다. 형식·ID 오류만 1회 보정하며 오류/판단 불가를 성공으로 숨기지 않는다.

## ADR-025 — 로컬 채팅 GraphRAG 활성화

- 2026-09-19 사용자 요청으로 로컬 `.env`만 GraphRAG=true로 전환한다. 신규 환경의 코드/Compose 기본값 false는 유지한다.
- 기존 Ollama 생성·임베딩과 PG 데이터를 보존하며 기본 검색 뒤 제한된 CITES 확장을 사용한다. 실패 시 기본 검색 유지, 원문/문서 단독 도구는 확장하지 않는다.
- 정확도 검증 완료나 공개 운영 승인으로 간주하지 않는다. 관계도 시각화·전체 컨텍스트 토큰 예산·복합 질문 전문가 검수는 후속이다. LLM Judge 구현은 보류한다.
- ADR-021의 로컬 활성화 시점만 변경하며 검색 안전 경계는 보존한다.

## ADR-024 — LangSmith로 평가 조회·검수 화면 교체

- 후속 사용자 지정: 키 파일은 .env.example로 변경하고 .env.langsmith는 삭제했다. Docker 포함 예외를 제거하며 실제 키가 있는 파일은 커밋하지 않는다. 아래 최초 키 격리 결정은 이 지정으로 대체한다.

- 사용자 요청에 따라 자체 대시보드 코드/실행기/전용 테스트를 제거하고 평가 CLI에 prepare/publish를 추가한다. ADR-023을 대체한다. runs/reviews 원본은 보존한다.
- 기존 scorer를 재실행해 저장 report와 일치할 때만 전송 계획을 만든다. 기본값은 본문 제외, 원문/답변 검수는 별도 include-content 선택. 계획 hash의 명시 승인 후에만 네트워크 Client를 만든다.
- 기존 결과를 reference dataset에 연결된 base/graph 실험으로 업로드한다. 새 추론이나 실서비스 trace로 소개하지 않는다. 초안 지표는 diagnostic 이름으로 구분하고 실제 소요 시간은 별도 feedback으로 기록한다.
- 키는 Git/Docker 제외 .env.langsmith에 격리하며 서비스 추적을 활성화하지 않는다. 원격 라벨을 로컬 정답으로 자동 승격하지 않고 수동 검수/변환/재채점한다.
- 원격 다단계 전송 실패는 부분 반영될 수 있다. 로컬 receipt 기록과 중복 실험 거부를 사용하며 자동 원격 삭제는 하지 않는다.

## ADR-023 — 평가 대시보드는 로컬 전용 별도 프로그램 (ADR-024로 대체)

- evaluation_dashboard와 scripts/evaluation_dashboard.py를 사용자 서비스 라우터·프런트엔드·Compose에 연결하지 않고 서비스 이미지에서도 제외한다.
- 127.0.0.1 바인딩, Host/Origin 검사와 저장 토큰을 사용한다. DB/모델/평가 실행 기능 없이 기존 결과 파일만 조회한다.
- 검수는 evaluation/reviews에 원본 해시·검수자·시각이 담긴 추가 전용 리비전으로 저장한다. 충돌은 거부하고 원본 보고서·정답셋은 수정하지 않는다.
- 답변 검수는 기존 Adjudication 규약으로 내보내고 근거 라벨은 승인 전 제안으로 내보낸다. 로컬 검수자 이름은 인증된 신원을 의미하지 않는다.

## ADR-022 — 평가 규약·관측·검수·실행을 분리

- 기존 eval_rag/eval_graph_rag의 지표 산출 코드와 안내 stub을 제거하고 evaluation 패키지와 scripts/evaluate.py로 통합한다. scripts는 얇은 실행 진입점, evaluation/cli.py는 인자·실행·종료 코드 처리를 담당한다. 과거 질문/결과 파일은 보존한다.
- 검색 판단은 required/supporting/irrelevant/hard_negative와 미판정 후보를 구분한다. 정확한 조·항·호·버전으로 비교하고 hard negative가 전체 반환 근거에 섞이면 별도 실패 처리한다.
- 공식 라벨 승인에는 인간 검수·기준일·출처/발췌·버전이 필요하다. 기존 39문항의 grounded 표시는 검수 이력을 대체하지 않으므로 전부 draft/dev로 이관한다.
- 파싱/관계/산술 합성 계약은 자동 판정하고 실제 세무 정확성과 섞지 않는다. 답변의 의미/근거성은 출력 hash에 결합된 인간 루브릭으로 검수하며 LLM 자기판정을 정답으로 승격하지 않는다.
- 선택 범위 gate와 배포 승인을 구분한다. 미수집/미판정은 incomplete, 어떤 실행 오류도 실패다. 반례가 실제로 fail 되는지 평가기 자신을 검증한다.
- 순차 live 어댑터는 기존 provider를 재사용하며 대화/PDF/법령 DB에 쓰지 않는다. 스냅샷은 해당 단계의 공개 데이터 의존성만 추적한다. 생성 호출은 --allow-generation으로 별도 허용한다.
- CI에는 합성 계약과 스키마/누출 검사만 연결한다. 모델/DB live 평가, 전문가 라벨 검수, 전체 채팅 trace 계측은 별도 범위다.

## ADR-021 — GraphRAG는 기존 검색을 대체하지 않는 보수적 보충 경로

- 기본 top-5와 직접 조회를 보존하고, 명시적 CITES와 원문 정의로 확인된 법/영 약칭만 1-hop 탐색한다. 계열명 일치만으로 관계를 생성하지 않는다.
- 약칭 정의는 전체 원문에서 유일해야 하며 정의 이후에만 사용한다. 정의 조문 버전 해시를 관계에 보존하고 조회 시 재검증한다.
- 역방향 인용은 같은 법령 계열만 허용한다. 최초 실험에서 다른 세목의 인용과 긴 본문이 추가되어, 키워드 필터·추가 4,000자 제한을 적용했다. 의미 리랭킹/법적 적용 판단은 아니다.
- 최대 3 seed/24 관계/2 추가 조문/3초, 실패 시 기본 결과 유지. 과거 시점 판단과 사용자 PDF를 그래프에 맡기지 않는다.
- 기본 비활성을 유지한다. 기존 단일 정답 골든셋은 이미 기본 검색 성공률이 높아 GraphRAG의 추가 가치를 측정하기 부족하다. 복합 법률–시행령 정답셋과 답변 검수 후 활성화한다.
- Neo4j는 기본 Compose에 포함하고 Graph 전용 overlay/호환 셸은 재생성하지 않는다. PG 스키마·임베딩은 변경하지 않는다.

## ADR-020 — 공통 도구 호출과 도메인 로직 분리

- 결정: tools의 planner·registry·executor가 JSON 선택과 실행 제한을 담당한다. native provider tool_calls에 의존하지 않는다.
- 법령 원문 조회는 law/lookup_service.py로 추출해 라우터·검색·도구가 공유한다. 사용자 문서 도구는 기존 user_id 격리 검색 SQL을 재사용한다.
- 계산기 엔진의 LLM 추출·키워드 게이트를 공통 도구 계층으로 이동하고 수작업 파라미터 목록 대신 요청 스키마로 도구 정의를 생성한다.
- 안전: 한 질문당 하나, 선택·실행 각각 30초, strict/extra-forbid 입력 검증. 인증 사용자 ID를 서버에서 주입하며 조회 실패·시간 초과를 답변 컨텍스트로 전달한다.
- 원문·문서 도구는 RAG·웹 중복 검색을 생략한다. 복합 질문의 다중 도구 연쇄 실행은 후속 과제다. 문서/도구 본문은 신뢰할 수 없는 자료로 취급한다.

## ADR-019 — LangChain은 provider 위의 조합·검증 계층에 적용

- 결정: `langchain-core`의 ChatPromptTemplate·Runnable·PydanticOutputParser를 사용하고 자체 HTTP provider는 유지한다. `ChatOllama`는 재도입하지 않는다.
- 적용: 최종 답변 생성·스트리밍, 세목 분류, 계산기 입력 추출, 인용 목록 추출. 시스템 프롬프트 내용은 유지하고 사용자·검색 텍스트를 템플릿 변수로만 삽입한다.
- 검증: 완전한 JSON인지 먼저 검사하고 타입·필수 필드·인용 형식 및 계산기 입력을 검증한다. 오류 시 기존 fallback을 유지하며 자동 LLM 재호출은 추가하지 않는다.
- 추적: 단계별 실행 이름과 프롬프트 버전 메타데이터를 부여한다. LangSmith SDK는 간접 의존성으로 설치되지만 원격 추적·평가 연결은 후속 작업이다.
- 영향: ADR-018의 HTTP 어댑터 결정은 유지한다. 미사용으로 제거했던 `langchain-core`는 실제 용도가 생겨 재도입한다.

## ADR-018 — Ollama 생성도 직접 HTTP 어댑터 사용

- 결정: `ChatOllama` 대신 `httpx`로 Ollama `/api/chat`을 호출한다. `LLMProvider` 규약과 서비스 공통 호출 함수는 유지한다.
- 이유: provider 연결을 자체 어댑터에 모으고 `langchain-ollama`에 대한 실행 의존성을 없앤다. 후속 코드 정리에서 사용처가 없는 `langchain-core`도 제거했다.
- 공통 호출 인자는 `max_tokens`로 통일한다. provider는 프로세스 단위로 재사용하고 종료 시 닫으며 설정 변경은 재시작으로 적용한다. 테스트용 HTTP 주입 전역 변수와 불완전한 설정 캐시 키를 제거했다.
- 구현: 일반 생성, JSON Schema, NDJSON 스트리밍을 지원하며 기존 `options`·`think`·`keep_alive`를 보존한다. HTTP timeout·연결 종료·스트림 오류 및 불완전 종료를 처리한다.
- 범위: 실행 엔진과 모델은 교체하지 않는다. 임베딩은 기존 HTTP 어댑터를 유지한다.

이 문서는 이미 해결한 문제를 다음 세션에서 되돌리거나 같은 논의를 반복하지 않기 위한 기록이다.

## ADR-001 — n8n 프로토타입에서 코드 기반 구조로 전환

- 결정: FastAPI·React·PostgreSQL 기반으로 재설계한다.
- 이유: 조문 단위 파싱, 법령 위계, 사용자 격리, 테스트, 로컬 모델, 마이그레이션을 세밀하게
  제어하기 어렵기 때문이다.
- 결과: 핵심 로직을 서비스 계층에서 테스트할 수 있고 배포 구성을 코드로 재현할 수 있다.

## ADR-002 — Ollama endpoint를 환경설정으로 추상화

- 결정: Ollama IP를 애플리케이션 코드에 하드코딩하지 않는다.
- 개발: `dev/docker-up-wsl.sh`가 WSL에서 Windows 호스트 주소를 탐지한다.
- 운영: Docker 서비스명 또는 사설 DNS를 사용한다.
- 이유: WSL2 NAT 주소는 재시작 시 달라질 수 있다.

## ADR-003 — readiness와 외부 AI 의존성 상태 분리

- 결정: `/health/live`, `/health/ready`, `/health/dependencies`를 분리한다.
- 이유: Ollama 장애가 인증·DB 조회·계산기까지 모두 사용할 수 없는 상태를 의미하지 않는다.
- Docker backend healthcheck는 DB와 Alembic 준비 상태를 기준으로 한다.

## ADR-004 — Alembic을 DB 스키마의 단일 변경 경로로 사용

- 결정: 기존 SQL 스키마를 legacy baseline으로 채택하고 이후 변경은 Alembic revision으로 작성한다.
- 이유: 빈 DB와 기존 볼륨의 상태 차이, 수동 SQL 적용 순서 문제, 배포 재현성 문제를 해결한다.
- 금지: 신규 기능을 위해 `db/migrations/*.sql`만 추가하고 수동 적용하는 방식.

## ADR-005 — 법령 참조 파싱을 법령 도메인 서비스에 배치

- 결정: 범용 `utils`가 아니라 `app/services/law/reference_parser.py`에 둔다.
- 이유: 조·항·호·목, 가지번호, 원문 항 기호는 대한민국 법령에 종속된 도메인 규칙이다.
- 본문 대조는 `structure_parser.py`, XML 수집은 `parser_service.py`로 책임을 분리한다.

## ADR-006 — `제59조의4`와 `제59조 제4항`을 다른 필드로 저장

- 결정: 조 가지번호는 `article_branch`, 항은 `paragraph`로 구분한다.
- 이유: `제59조의4`의 4는 항이 아니라 제59조에서 파생된 독립 조문 번호다.
- 같은 원칙을 `item`과 `item_branch`에도 적용한다.

## ADR-007 — 조문 전체 벡터와 항 벡터를 함께 사용

- 결정: 조문 전체 임베딩을 유지하면서 긴 조문의 항 단위 보조 임베딩을 추가한다.
- 이유: 조 전체만 사용하면 특정 항의 의미가 희석되고, 항만 사용하면 조 전체 맥락 질문이 약해진다.
- 검색 히트가 항 벡터여도 최종 컨텍스트는 필요한 법적 맥락을 포함해야 한다.

## ADR-008 — 법적 권위와 유사도를 분리

- 결정: 검색 유사도와 별개로 법률 → 시행령 → 시행규칙 → 유권해석 순의 우선순위를 적용한다.
- 이유: 의미적으로 비슷한 하위 자료가 상위 법령보다 먼저 제시되는 것을 방지한다.

## ADR-009 — 세액 계산을 LLM에서 분리

- 결정: LLM은 계산기 선택과 입력 추출을 담당하고 실제 세액은 DB 세율표 기반 함수가 계산한다.
- 이유: 산술 환각을 줄이고 계산 단계와 법적 근거를 재현 가능하게 만든다.

## ADR-010 — scripts는 얇은 CLI 진입점으로 유지

- 결정: 수집·동기화·백필·평가의 인자 처리와 실행만 `scripts/`에 둔다.
- 핵심 로직은 `app/services/`에 둔다.
- 장시간 또는 변경 작업은 dry-run·명시적 옵션·종료 코드로 안전하게 제어한다.

## ADR-011 — 채팅 접근제어와 AI HTML 정화를 렌더링 전에 강제

- 결정: 일반 채팅과 SSE 채팅은 LLM 또는 스트리밍을 시작하기 전에 `conversation_id`가 로그인 사용자 소유인지 DB에서 확인한다.
- 결정: 잘못된 UUID, 없는 대화, 타인 소유 대화는 모두 같은 404를 반환하여 대화 ID 존재 여부를 노출하지 않는다.
- 결정: AI Markdown은 `marked` 변환 후 DOMPurify로 정화한 HTML만 DOM에 삽입한다.
- 결정: Docker 빌드 컨텍스트에서는 `.env`와 `.env.*`를 제외하고 공유 가능한 `.env.example`만 허용한다.
- 이유: 인증 여부만으로는 객체 단위 접근권한을 보장할 수 없으며, 생성형 답변과 검색 문서는 신뢰할 수 없는 입력이므로 저장형 XSS와 이미지 레이어의 비밀정보 잔존을 별도로 차단해야 한다.

## ADR-012 — 생성 LLM은 vLLM, 기존 임베딩은 Ollama로 분리

- 결정: 생성 요청은 OpenAI 호환 vLLM 서버로 전환하고, 기존 2560차원 임베딩과 선택적 리랭킹은 Ollama에 유지한다.
- 이유: 생성 provider를 교체하면서 기존 pgvector 데이터를 전면 재임베딩하지 않고 점진적으로 전환하기 위함이다.
- 개발: `docker-compose.vllm.yml`을 overlay로 적용하며 `LLM_PROVIDER=vllm`과 내부 DNS `http://vllm:8000/v1`을 사용한다.
- 자원 제약: 12GB GPU에서 9B 생성 모델과 4B 임베딩 모델을 번갈아 사용하므로 생성 모델은 NVFP4 체크포인트, 제한된 KV cache와 동시 요청 수로 실행한다.
- 실제 런타임 결정: 10.43GiB는 다운로드 체크포인트 크기이며 실제 가중치 VRAM 사용량으로 간주하지 않는다. `--language-model-only`, `--enforce-eager`, 2,048 토큰, 동시 시퀀스 1개를 사용한다. Qwen3.5 하이브리드 구조에서 품질 저하가 보고된 FP8 KV cache 강제 설정은 제거하고 기본 dtype을 사용한다. CPU offload는 Qwen GDN Triton 커널과 호환되지 않아 사용하지 않는다.
- 복구: 기본 Compose와 `dev/docker-up-wsl.sh`는 Ollama 생성 provider의 fallback으로 유지한다.

## ADR-013 — 검색 모델 조합 확정

- 생성: `Qwen3.5-9B NVFP4`를 vLLM으로 서빙한다.
- 임베딩: 기존 `Qwen3-Embedding-4B`와 2560차원 pgvector 데이터를 유지한다.
- 리랭커: `dragonkue/bge-reranker-v2-m3-ko`를 신규 도입한다.
- 이유: 이미 검증·구축된 임베딩을 보존하면서, 한국어 금융 문서 평가 근거가 있는 경량 Cross-Encoder로 후보 조문의 최종 정렬을 개선한다.
- 검색 순서: BM25·벡터 검색 후보 생성 → 리랭커 → 법령 위계 및 직접 조문 일치 규칙 → 최종 컨텍스트 선정.
- 구현: 임베딩과 리랭커의 provider 선택지는 Ollama와 Infinity로 제한하며 애플리케이션은 역할별 adapter를 통해 호출한다.
- 주의: 현재 PC에서 Infinity 전체 모델 로딩은 완료되지 않았으며 적용 전후 골든셋 회귀 평가도 후속 작업이다.

## ADR-014 — 추론 역할과 연산 장치 분리

- 결정: LLM·임베딩·리랭커의 provider와 endpoint를 독립 설정하고, Infinity 임베딩과
  리랭커를 별도 컨테이너로 실행한다.
- 결정: 임베딩·리랭커는 환경변수와 `dev/set-inference-device-wsl.sh`를 통해 CPU/GPU를
  전환할 수 있게 하되, 12GB GPU에서는 vLLM과 다른 모델의 GPU 동시 상주를 차단한다.
- 이유: 장치 배치를 코드에 고정하지 않으면서 GPU OOM과 서비스 전체 재시작을 방지한다.

## ADR-015 — 소규모 서비스 기본 추론 엔진을 llama.cpp로 전환

- 결정: 생성 LLM과 신규 임베딩은 GGUF Q4_K_M 모델을 독립 llama-server로 서빙한다.
- 생성 모델은 `unsloth/Qwen3.5-9B-GGUF:Q4_K_M`, 임베딩은
  `Qwen/Qwen3-Embedding-4B-GGUF:Q4_K_M`을 사용하고 임베딩 pooling은 `last`로 고정한다.
- 이유: 단일 사용자·소규모 서비스에서는 vLLM의 높은 동시 처리량보다 낮은 상주 메모리,
  NVIDIA·Apple Silicon 간 GGUF 이식성, 단순한 OpenAI 호환 API 운영이 더 중요하다.
- 기존 Ollama 경로는 v1 호환을 위해 보존한다.

## ADR-016 — vLLM·Infinity 실험 구성 제거

- 결정: vLLM·Infinity 전용 Compose, 실행 스크립트, provider 선택지, Docker 이미지와 모델
  캐시를 제거하고 llama.cpp·Ollama 두 경로만 유지한다.
- 이유: 12GB VRAM PC에서 생성·임베딩·리랭커의 동시 상주가 불안정했고, 소규모 운영 목표에는
  GGUF 기반 llama.cpp가 메모리와 플랫폼 호환성 측면에서 더 적합하다.
- 영향: ADR-012~014는 실험 당시의 기록으로만 남으며 현재 운영 결정은 ADR-015~016이 대체한다.

## ADR-017 — TEI·리랭커 구성 제거

- 결정: 미사용 TEI 이미지와 리랭커 모델 캐시 및 애플리케이션 리랭킹 계층을 제거한다.
- 이유: 현재 PC에서 세 모델 동시 상주가 어렵고, 검증되지 않은 리랭커 경로를 유지하면 운영·상태
  진단 복잡도만 증가한다. 검색은 벡터·BM25·RRF와 법령 위계 규칙으로 동작한다.
- 영향: 과거 리랭커 관련 ADR은 실험 기록으로만 남는다.
- 저장 벡터는 엔진·양자화 변경 시 재사용하지 않는다. llama.cpp 결과는 `embedding_v2`에
  백필하고 골든셋 평가를 통과한 뒤 활성 검색을 v2로 전환한다.
# 2026-09-07 계산 실패는 금액이 아니다

- 필수 세율·공제 누락은 보수적 실패로 처리하고 임의 상수로 대체하지 않는다. 정상 계산의 0원 및 환급액은 허용한다.
- API 오류에는 code/message/retryable만 공개하고 DB 예외 원문은 출력하지 않는다. 도구 선택과 인자 검증은 분리해 입력 부족을 선택 실패와 구분한다.
- 계산 실패 답변은 프롬프트 경고만으로 보호하지 않고 최종 생성 단계를 우회한다. 일시 장애는 사용자 재시도를 안내하되 자동 재시도하지 않는다.

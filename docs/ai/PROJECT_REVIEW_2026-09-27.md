# 프로젝트 분석 및 개선 제안 — 2026-09-27

## 검토 범위와 결론

프로젝트 문서, FastAPI 인증·채팅·검색·문서·계산 서비스, React 문서 검토 흐름, Compose/Nginx, CI와 평가 데이터를 검토했다. 이번 작업은 분석·해결책 제안이며 서비스 코드 수정, 재배포, 데이터 보정, 외부 생성 호출은 수행하지 않았다. 작업 시작 때 존재한 수정 파일 19개의 변경을 보존했다.

공식 법령과 사용자 문서의 구분, 사용자 소유권 검사, 현행/과거 법령 분리, LLM과 계산기 분리, Alembic, 평가 도구가 갖춰져 있다. 다음 투자는 **인용 검증의 오탐 제거, 금액의 정확성, 사용자 확인값의 원본 연결, 배포 경로 검증**에 우선 배정하는 것이 좋다. 테스트 통과는 실제 세무 정답성 검증을 대체하지 않는다.

## P1 — 우선 수정할 항목

### 1. 인용 검증이 서로 다른 근거를 결합해서 통과시킨다

**근거:** `app/services/citation_guard.py:56`은 합쳐진 컨텍스트에서 법령명과 조문번호를 각각 부분 문자열로 찾는다. 두 값이 같은 근거에 속하는지 검사하지 않고 항·호·목과 버전도 검증 키에 포함하지 않는다.

**재현:** 근거가 `소득세법 제1조`와 `법인세법 제2조`일 때 답변의 `소득세법 제2조`가 통과한다. `제59조의4`만 있어도 `제59조`가 통과한다. `제1조 제99항`을 인용해도 항은 추출되지 않아 조 수준에서 통과한다. 법적 해석 이전의 식별 오류다. 과거 법령 전용 검증 전체에 같은 결함이 있다는 의미는 아니다.

**해결책:** `법령 ID + 버전/hash + 조/가지번호 + 항/호/목 + 출처 종류`를 가진 근거 객체를 유지한다. 기존 reference_parser/structure_parser를 재사용해 답변 인용을 같은 객체와 정확히 대조한다. 조문 존재와 설명의 의미적 근거성을 별도 상태로 표시한다. 제목 교정은 인용 검증을 대신하지 못한다.

**완료 기준:** 위 3건과 다른 법령·시행령·버전 혼동을 거부하고 일반/SSE/재생성 경로에서 동일한 검증 결과를 반환한다. 근거 없는 결론에 대한 경고·응답 보류 정책도 정한다.

### 2. Decimal이 float로 바뀌며 금액에 1원 오차를 만든다

**근거:** `app/services/calculator/brackets.py:14`는 rate를 float로 변환한 뒤 곱하고 int로 절사한다. 다른 공제·가산세 계산에도 같은 패턴이 있다.

**재현:** 위의 180 × 0.35 합성 입력이 62를 반환했다. 이는 산술 함수 반례이며 실제 세법의 특정 구간이나 신고세액 사례를 주장하는 것은 아니다.

**해결책:** 금액·비율 연산을 끝까지 Decimal 또는 정수 비율로 유지한다. 코드 상수는 문자열에서 Decimal로 만들고 DB NUMERIC을 float로 바꾸지 않는다. 단계별 절사 시점·단위를 명시한다. 십진 표현과 반올림 제어는 [Python 공식 문서](https://docs.python.org/3/library/decimal.html)를 참고한다.

**완료 기준:** 0, 구간 경계 전후, 소수 세율, 큰 금액, 공제·가산세를 정수/Decimal 기준값과 비교한다. 법적 절사 규칙은 세목별 공식 근거 검수가 필요하다.

### 3. 문서 금액 후보가 소수점 앞부분을 버린다

**근거:** `app/services/document_review_service.py:16`의 AMOUNT_RE는 정수만 인식하고 소수점 뒤 숫자의 매칭 시작을 막지 않는다. candidates()는 매칭 금액에 억/만 단위를 곱한다.

**재현:** `1.5억원` → `5억원` 매칭 → 현재 환산 방식상 500,000,000원 후보. 사람이 확인하는 흐름이 있어 자동 계산 반영은 막고 있지만 확인 화면에서 틀린 숫자를 제안한다.

**해결책:** 소수 단위를 지원하는 금액 파서를 분리하고 Decimal로 환산한다. 지원하지 않는 숫자 표기는 부분 매칭 대신 추출을 보류한다. 원문 span, 단위, 부호, 위치를 후보와 함께 유지한다.

**완료 기준:** `1.5억원`, `2.75만원`, `1억 5천만원`, 쉼표, 괄호/음수, 표의 단위 표기에 대해 정확한 값 또는 추출 보류를 검증한다. OCR 정확성은 별도 평가한다.

### 4. 화면의 50MB 제한과 Nginx의 실제 제한이 다르다

**근거:** 서버·UI는 50MB를 허용하지만 `frontend/nginx.conf:14` 및 실행 중 `nginx -T`에 client_max_body_size가 없다. 기본 1m 제한과 초과 시 413 응답은 [Nginx 공식 문서](https://nginx.org/en/docs/http/ngx_http_core_module.html#client_max_body_size)에 명시돼 있다. 실제 2MiB 요청의 프록시 차단도 확인했다.

**해결책:** 업로드 경로의 요청 본문 한도를 파일 50MiB에 multipart 여유분을 더해 설정한다. 앱은 파일 자체의 50MiB 한도를 유지하고 UI는 HTML 형식 413도 이해 가능한 메시지로 처리한다.

**완료 기준:** 실제 frontend 경유 1MiB 초과·50MiB 경계·50MiB 초과를 검사한다. 서버 직접 호출 및 작은 파일 테스트만으로 완료 처리하지 않는다.

### 5. 이전 문서의 확인값이 교체된 새 원본에 연결될 수 있다

**근거:** `app/routers/upload.py:30`과 `frontend/src/components/Documents/DocumentReview.jsx:23`의 저장 요청에는 확인한 문서 hash가 없다. `document_review_service.py:79`는 저장 시점의 최신 원본 hash를 붙인다. 행 잠금은 사용자가 어떤 버전을 보고 있었는지를 증명하지 못한다.

**재현 조건(코드 확인, 실DB 경쟁 실험 미수행):** 탭 A에서 검토 → 탭 B에서 같은 이름의 새 PDF 업로드 → 탭 A가 이전 금액 저장. 새 PDF의 페이지 범위 안이면 이전 입력을 최신 hash로 저장할 수 있다.

**해결책:** 읽은 expected_sha256/version을 필수로 전달하고 저장 트랜잭션에서 원본과 불일치하면 409를 반환한다. 검토값 자체도 revision/ETag로 여러 탭의 덮어쓰기를 막는다. 장기적으로 파일명 대신 document_id와 불변 version_id로 상담·원본·검토값을 연결한다.

**완료 기준:** 오래된 화면 저장 거부·재조회 안내, 동일 이름 동시 업로드의 청크/원본 일관성, 상담으로 적용되는 검토값의 버전 일치 검증.

## P2 — 품질과 운영 안정화

### 6. 과거 계산의 자료 조회일과 계산 규칙 버전이 다르다

DB 세율·공제 조회에는 as_of가 있지만 `gift_tax.py:53`의 신고공제 비율, `penalty_tax.py:19`의 일일 비율 등은 코드 상수다. 참고 계산 안내는 유용하지만 과거 사건 재현성을 보장하지 않는다. get_source_articles도 실제 사용한 행만 전달하지 않고 세목의 최신 출처를 별도로 모은다.

**제안:** Alembic으로 규칙 유효기간·적용 조건·근거 버전·규칙 식별자를 관리한다. 결과에 실제 사용한 row ID/hash와 계산기 버전을 저장한다. 검수한 기간·조건 밖의 계산은 지원 범위를 안내하고 중단한다. 우선 한 세목의 검수된 사례를 완성한 뒤 확장한다. 이번 검토는 각 상수의 현행 법적 적정성을 판정하지 않았다.

### 7. GraphRAG 장애가 의존성 상태에 드러나지 않는다

조회 시점에 GraphRAG는 활성화됐지만 tax_neo4j는 종료돼 있었다. 종료 코드 137만으로 OOM이라고 단정할 수 없고 OOMKilled는 false다. 원격 Neo4j로 별도 연결되는지는 이번 상태 조회만으로 확정할 수 없다.

`app/routers/health.py:166`의 dependencies는 DB·생성·임베딩을 검사하고 Neo4j를 포함하지 않는다. GraphRAG 실패 시 기본 검색으로 돌아가는 설계는 유지하되 기능 저하를 관측해야 한다.

**제안:** graph enabled/connected/degraded, 마지막 성공 시각, 확장 성공/실패 횟수를 추가한다. DB 중심 readiness는 유지하고 선택 기능 장애는 별도 표시한다. 재기동 전 컨테이너/호스트 이벤트와 실제 endpoint 연결을 조사한다. 이번 분석에서 재시작하지 않았다.

### 8. 테스트 수와 실무 품질을 연결하는 검증 단계가 부족하다

CI는 Python 테스트·평가 계약·Alembic head 개수를 검사한다. frontend 테스트/빌드, 실제 프록시 업로드, 빈 PostgreSQL의 마이그레이션 적용, 브라우저 핵심 흐름은 CI에 연결돼 있지 않다. 기본 API fixture는 DB mock이며 Neo4j 통합 테스트는 opt-in이다. retrieval의 draft 라벨과 관계 평가의 인간 골드 미완료는 이미 문서에 명시돼 있다.

**제안:** 빠른 PR 검사에 frontend test/build와 P1 반례를 넣는다. 별도 통합 job에서 임시 PostgreSQL의 Alembic upgrade, 사용자 간 접근 차단, 동시 업로드, 프록시 경유 파일 크기, SSE 실패/재생성을 검증한다. AI 평가는 전문가 승인 gold와 모델·프롬프트·데이터 버전을 기록한다.

**품질 지표:** 정확한 법령/버전/항·호 식별률, 필요한 근거 재현율, 잘못된 근거 채택률, 금액 일치율, 근거 부족 시 응답 보류, 최초 출력 지연과 전체 응답 p95. 수치는 측정한 뒤 목표를 정한다.

### 9. 요청 단위 자원·비용 제한과 문서 작업 재개가 부족하다

출력 토큰 상한·도구 timeout·최근 3턴 제한·Graph 보충 예산은 있지만 일반 채팅의 history+검색 원문+도구+출력을 합친 입력 예산은 없다. format_hybrid_context는 검색 조문 전체를 합친다. 1회 출력 한도는 연속 생성·보조 호출까지 포함한 총비용 한도가 아니다. 앱/Nginx에서 사용자별 요청률·동시 생성·업로드 누적량 제한은 확인하지 못했다.

문서 추출은 to_thread로 옮겼지만 추출→분류→임베딩은 한 HTTP 요청에서 실행한다. PDF 검토의 pypdf 추출, bcrypt 해싱은 async 함수 안에서 동기 실행된다.

**제안:** 전역/사용자별 동시 작업 상한, 요청 deadline, 입력·출력 총 토큰 예산과 측정치를 추가한다. 문서는 영속 job 상태·진행률·재시도·중복 방지 키를 갖춘 worker로 분리한다. CPU 작업은 제한된 실행 풀에 격리한다. 단일 서버라면 PostgreSQL job 테이블부터 시작해도 된다.

### 10. 인증·개인정보·복구 정책을 제품 동작과 맞춘다

- 회원가입은 비밀번호 최소 1자, 변경은 8자로 정책이 다르다. bcrypt 설정은 byte 초과를 절단하지만 입력 제한은 문자 수이므로 다국어 비밀번호 경계도 검토해야 한다.
- verify_token은 JWT 서명/만료를 확인한다. 비밀번호 변경·로그아웃 시 기존 토큰을 무효화하는 서버의 버전/세션 검사는 없다.
- delete_account의 여러 DELETE가 하나의 트랜잭션으로 묶이지 않아 중간 실패 시 부분 삭제 가능성이 있다.
- 문서 분류는 이름과 도입부 최대 800자를 설정된 LLM으로 보낸다. 채팅/tracing도 본문을 보낼 수 있지만 README 일부는 외부 전송 없는 로컬 처리를 단정한다.
- dev/scripts/.github에서 자동 백업·복원 검증 코드를 찾지 못했다. 별도 수동 백업 존재 여부는 미확인이다. 원본 파일도 PostgreSQL에 들어가므로 용량·보관·삭제 정책이 필요하다.

**제안:** 비밀번호 정책 통일·로그인 시도 제한·token version, 계정 삭제 트랜잭션을 적용한다. 생성/분류/추적 각각의 외부 전송 정책과 로컬 전용 모드를 마련하고 로그의 파일명·이메일 최소화를 검토한다. 암호화된 DB 백업과 임시 DB 복원 시험을 운영 절차로 만든다. 법적 준수 여부는 이번 코드 검토로 판정하지 않았다.

## P3 — 검색 구조와 유지보수

현행 hybrid_search_service는 공식 조문/사용자 문서 벡터, 직접 조문 조회, 멀티쿼리 RRF를 결합한다. 확인한 app/db/alembic에는 BM25/tsquery 검색 경로가 없지만 일부 설계 문서는 BM25를 포함한 것으로 설명한다. 먼저 문서 표현을 실제 구조에 맞추고 키워드 검색·리랭커는 전문가 gold로 비교해 채택한다.

RRF 중복 키는 content 문자열이므로 동일 본문의 다른 법령·버전·출처가 합쳐질 수 있다. 법령/버전/조문/문서 ID를 키로 사용해 출처를 보존한다. 직접 조문 결과·관련성·법령 위계의 적용 순서는 별도 평가한다.

chat_service는 일반/SSE, 검색, 후처리, 저장, tracing을 함께 담당한다. 공통 준비 결과와 검증 결과 객체를 두어 일반·SSE·재생성 중복을 줄인다. CURRENT_STATUS와 README는 최신 상태 요약과 변경 이력을 분리한다. 일괄 리팩터링보다 결함 수정 경계부터 작게 분리하는 편이 좋다.

## 제안 실행 순서

1. **첫 수정 묶음:** 인용 검증, Decimal 산술, 금액 파서, Nginx 업로드 제한, 검토값 버전 검사. 재현 반례를 회귀 테스트로 고정한다.
2. **다음 안정화 묶음:** Neo4j 장애 가시화·원인 조사, frontend/DB/프록시 CI, 인증 폐기 정책과 계정 삭제 트랜잭션, 백업·복원 시험.
3. **품질 검수와 처리량 개선:** 한 세목의 검수된 규칙 버전·gold를 확보하고 전체 입력 예산·동시 요청 한도·문서 worker를 도입한다. 이를 기준으로 GraphRAG/검색 변경 효과를 측정한다.

전문가 검수·법령 적용 규칙 확정은 자동 코드 수정과 분리해야 한다. 추가 법령 수집·그래프 확대·새 세목 확장은 현재 검증 결함을 해결한 뒤 우선순위를 다시 정한다.

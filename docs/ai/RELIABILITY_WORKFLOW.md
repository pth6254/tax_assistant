# 질문·도구·근거·주장 검증 흐름

구현일: 2026-09-28. 생성/계획/Judge 기본 설정은 기존 OpenRouter GPT-6 Luna를 상속하고 임베딩은 기존 Ollama를 유지한다.

## 실행 경로

1. 단순 명시 원문/사용자 문서 조회와 계산은 `tools/planner.py` → `tools/policy.py`에서 요청 목적과 입력 출처를 확인한다. 조문을 언급하며 의미를 묻는 질문은 원문 조회 요청으로 취급하지 않는다. 도구가 필요 없는 상태와 입력 부족을 구분한다.
2. 분석·복합 요청은 `question_planning.py`에서 `QuestionPlan`으로 나눈다. 주체, 세목, 사용자 원문 발췌, 날짜, 가정, 의존 작업을 유지한다. 모델 계획이 원문 또는 필수 세목을 누락하면 서버의 보수적 계획을 사용한다. 알파벳 회사명이 아닌 일반 주체의 완전한 분해는 여전히 모델 평가 대상이다.
3. `reliable_workflow.py`는 쟁점별 공식 법령 검색과 최대 4개 도구 실행을 조정한다. 사용자 문서 검색은 소유권 필터를 유지한다. 독립 쟁점은 다른 도구 실패로 중단하지 않는다. 실패한 작업과 의존 결론은 분리한다.
4. `claim_verification.py`는 쟁점별로 생성·Judge를 실행한다. 생성 모델은 짧은 근거/원문 구간 ID를 schema enum에서 선택하고 서버가 영구 근거 ID와 정확한 발췌를 복원한다. 원본·범위·인용 코드 검사와 별도 Judge를 모두 거친다. 부족한 분석 쟁점만 1회 재검색/재생성하며 이미 통과한 내용을 보존한다.
5. 검증 결과에 따라 공개할 주장 또는 도구 원문/계산 결과를 조립한다. 조립 후 추가 자유 생성은 하지 않는다. JSON 응답과 SSE는 같은 함수를 사용한다. 생성 초안은 SSE로 보내지 않는다.

## 근거의 신뢰 경계

- `EvidenceRecord`는 검색 서비스가 만든다. DB 원본 ID, 출처 종류, 원문 해시, 조회 본문 해시, 조문, 시행일을 보존한다. 현재 법령 버전 ID는 원본 행 ID·시행일·원문 해시로 식별하는 스냅샷 키다. 공식 MST 버전이나 적용기간 전체를 새로 확인했다는 뜻은 아니다.
- `EvidenceContext`는 기존 문자열 프롬프트와 호환되는 어댑터다. 검사는 문자열을 파싱하지 않고 `records`를 사용한다. 문자열을 합치거나 자르면 출처 정보가 사라지므로 보존이 필요한 곳은 `with_text` 또는 `context_from_records`를 사용한다.
- 사용자 업로드는 분류 category가 법령이어도 `origin=user_document`다. 문서 청크 ID/해시는 검색한 청크의 식별자이며 업로드 파일 전체의 해시가 아니다. 업로드 본문의 출처 표식·URL·명령은 공식 권위를 부여하지 않는다.
- 원문 해시 불일치, 원본 ID 부재, 미래 시행 자료를 공식 인용 근거로 인정하지 않는다. 시행일 미상은 적용 시점 확인으로 표시하지 않는다.
- 레거시 파싱 손실 중 `다음 각 호`라는 문구 뒤에 실제 번호 목록이 없는 경우를 감지해 해당 검색 단위를 제외한다. 이 검사는 모든 파싱 오류를 검출하거나 원문 수집의 완전성을 증명하지 않는다.
- 제외 전 `source_recovery.py`가 동일 MST·법령명·시행일의 기존 공식 XML 스냅샷을 조회할 수 있다. 원본 해시 및 파싱한 법령명·시행일·공포일이 일치하고 완전한 목록을 읽을 때만 원문 조회/쟁점 검색에 사용한다. 출처 ID는 보관 스냅샷을 가리킨다. 기존 저장 행·임베딩·GraphRAG 관계의 대량 수정은 없다.
- 웹 검색 스니펫은 조문 발견에만 사용한다. 발견한 조문의 검증 가능한 DB 원문을 확보해야 근거가 된다. 임의 웹 본문을 공식 자료로 승격하지 않는다.
- 현재 조문 경로로 과거 적용을 확정하지 않는다. 기존 `law_history` 별도 경로는 유지하며 그 경로가 새 의미 Judge를 통과했다고 표시하지 않는다.

## 도구 입력

계산 요청 여부, 지원 세목, 필수 필드, 입력 타입과 필드별 사용자 발언을 확인한다. 이전 AI 답변을 입력 출처로 인정하지 않는다. 0·false·공제인원 등 계산기 기본값도 사용자 확인 없이 적용하지 않는다. 복합 한글 금액이나 입력 역할을 확정할 수 없는 문장은 재확인을 요구할 수 있다. 이미 사용자가 직접 입력하는 별도 계산기/상담 API의 계약은 바꾸지 않았다.

금액·연도·조문 번호·공제 설명은 계산 요청으로 간주하지 않는다. 명시적으로 금액 산출을 요청해야 하며 입력 부족 안내는 누락 필드 이름을 포함한다. 선택기 JSON 실패는 선택 오류로 구별한다. 금융/이자/배당소득 종합과세 전용 계산은 미지원이고, 현재 일반 소득세 계산기로 대신 실행하지 않는다.

## Judge 모드와 운영자 평가

- `ANSWER_JUDGE_MODE=shadow`가 기본이다. 코드상 출처·인용 오류는 즉시 차단한다. 법적 주장과 근거 확인 지침은 shadow 설정에서도 의미 Judge의 지원·적용 판정을 공개 조건으로 사용한다. 다른 주장 종류에는 기존 shadow/enforce 설정을 적용한다. Judge 판정만으로 법적 정확성이 확인됐다고 표시하지 않는다.
- `ANSWER_JUDGE_MODE=enforce` 구현은 지원/적용 판정이 모두 supported인 주장만 공개한다. unknown, 오류, 시간 초과는 통과가 아니다. 코드 검사 실패도 항상 차단한다.
- **이번 변경으로 전문가 정답률 교정이 완료된 것은 아니다.** enforce 운영 승격 전, 승인된 독립 골드에서 오답 통과·정상 답변 차단·미판정·쟁점 누락을 측정해야 한다. 모델 자신이 만든 정답을 독립 골드로 승인하지 않는다.
- `question_planning`, `answer_judge`가 고정 LLM 호출 목적에 추가됐다. `LLM_TASK_QUESTION_PLANNING_*`, `LLM_TASK_ANSWER_JUDGE_*` 설정으로 기존 provider facade를 통해 분리할 수 있다. 제공자나 모델은 이번 작업에서 교체하지 않았다.
- `answer_release`와 `claim_judge` trace가 기존 LangSmith 설정을 따른다. 후보 주장과 근거는 Judge trace, 최종 버전의 검사 요약은 답변 metadata에 연결한다. 추적 할당량/전송 실패는 검사 통과를 뜻하지 않는다.
- 평가 adapter `answer_reliable_context`는 명시적인 `input.evidence`와 `input.plan`을 읽어 실제 주장 생성·검사 함수를 실행한다. 기존 `--allow-generation`을 요구하고 대화 DB에는 쓰지 않는다. `input.context`는 독립 정답으로 별도 유지한다.
- LangSmith 게시 준비는 verification v2의 항목별 진단 지표를 `diagnostic.runtime.*`로 내보낸다. 독립 전문가 판정과 자동 진단의 이름 공간을 혼합하지 않는다. 별도 관리자 화면은 만들지 않는다.

## 사용자 화면과 저장

`planning / retrieving / generating / checking` 진행 상태와 최종 검사를 SSE로 보낸다. 답변과 검사 결과는 기존 JSONB metadata에 함께 저장되며 답변 재생성·버전 선택 시 복원된다. 근거 패널은 답변에 사용한 원문 스냅샷·시행일·문서 위치를 표시한다. 현재 조문으로 다시 조회한 내용을 당시 사용한 원문처럼 표시하지 않는다.

## 제한과 데이터 후속

- 초기 검색은 한 번에 동시 2개, 전체 검색 회차 90초, 도구별 45초 및 최대 4개, 답변 생성/검사 전체 240초로 제한한다. 준비 단계와 답변 단계는 별도 예산이다. 준비 단계에서 충족 검사 후 부족한 분석 쟁점만 1회 재검색하고, 답변 검증에서도 누락된 분석 쟁점만 최대 1회 보완 검색·재생성한다. 답변 단계의 보완 질의 생성에는 30초를 둔다.
- 2026-09-28 현행 DB의 부가가치세법 제39조 160자·제60조 1,606자에서 하위 목록 누락을 확인했다. 동일 MST 276117·시행일 2026-01-02의 스냅샷 128을 대조하는 읽기 경로는 각각 1,062자·4,629자를 반환한다. 원본 저장 행은 그대로이며 전체 재수집/임베딩 백필은 실행하지 않았다. 동일 버전 스냅샷이 없거나 손상된 자료는 계속 제외한다.
- 실모델 H/I 사례 실행에서 쟁점 분해, 근거 ID 검사, 부분 답변, 재검색, Judge 응답을 확인했다. 이는 세무 정답률 입증이 아니다. 당시 GraphRAG는 ValueError로 기본 검색에 복귀했으나, 이후 종료된 Neo4j를 다시 기동하고 백엔드 기동 스크립트에 그래프 의존성 준비를 추가해 동일 쟁점의 확장을 재검증했다. 원래 ValueError의 상세 스택은 당시 로그에 없어 확정하지 않았다.
- `dev/probe_reliable_answer.py`는 공개된 H/I·금융소득·일반 매입세액·증여 복합질문 예제로 실제 모델과 검색을 실행하며 대화·법령 DB를 변경하지 않는다. 명시한 새 파일에만 결과를 쓴다. `--inspect`는 관련 원문 길이와 동일 버전 보관 스냅샷의 공개 메타데이터를 확인한다.

## 2026-09-28 쟁점 검색 확장

- 분석 쟁점의 분리 기준은 사용자 요청 종류(원문·문서·계산·법적 분석), 거래 주체×세목, 독립된 사실 확인 목적이다. 기존 계획 검증은 주체·세목·명시 조문·시점을 원 질문과 대조한다.
- 각 분석 쟁점은 원래 질문과 짧은 요건 질의로 벡터 후보를 수집한다. 별도 한국어 키워드 검색은 현행 공식 법령에만 적용하고, `pg_trgm` 인덱스를 Alembic 0009로 관리한다. 후보는 조문 식별자 기준 RRF로 합친 다음 GraphRAG 확장을 적용한다.
- `issue_coverage.py`는 검증된 공식 근거의 쟁점 관련성과 요건·예외·효과 충족을 구조화 Judge로 평가한다. 결과의 근거 ID는 서버 후보와 대조한다. `missing` 쟁점은 부족 요건으로 한 번 재검색한다. `unverified` 쟁점은 법적 주장을 보류한다. `missing`은 쟁점 전체의 미완결을 뜻하며, 공식 근거와 개별 의미 검사를 모두 통과한 주장만 부분 공개한다.
- Judge 입력은 쟁점별 독립 호출(동시 최대 3개)로 보내며 ID를 해당 쟁점의 후보로 제한한다. 재검색 후 재평가가 형식 오류를 내면 기존 `missing` 판정을 보존하고 오류를 별도 기록한다. 가공 세금계산서 질의의 fallback 계획에서는 질문에 명시된 수취자·발급자를 구분해 세목별 두 검색어를 만든다.
- 실모델 H/I 진단은 실행 간 출력 변동이 있었고, 세목 또는 주체가 다른 주장이 생성된 사례도 확인했다. 코드 범위 검사로 관측한 유형을 막지만 모든 세무 의미 오류를 포괄하지 않는다. 네 세목의 답변 완결성은 아직 입증되지 않았다.
- 생성 컨텍스트는 쟁점마다 45,000자 예산 안에서 완전한 조문을 선택한다. 근거 충족 평가도 조문 뒤쪽을 1,600자로 자르지 않고 전체 단위로 읽는다. 의미 Judge에는 실제 인용한 조문만 전달한다. 의미 Judge와 자동 평가는 법적 정답률의 독립 입증이 아니다.
- 답변 생성·검증은 동시 최대 3개, 첫 회차 130초·보완 검색 40초·재시도 60초 안에서 완료된 쟁점을 보존한다. JSON·ID 오류는 같은 근거로 재시도하며 근거 부족 판정일 때만 재검색한다.
- 실제 OpenRouter 응답에서 이 계정의 GPT-6 Luna 분당 20회 제한을 확인했다. `OPENROUTER_REQUESTS_PER_MINUTE` 기본값 18로 계획·평가·생성·재시도 호출에 공통 간격을 적용한다. 제한은 단일 프로세스 내 계정/모델 단위이며 다중 worker·다른 프로그램은 공유하지 않는다.

## 검증

회귀 테스트는 위조 출처, 해시 불일치, 미래 자료, 누락된 호 목록, 잘못된 입력 역할, AI 메시지의 숫자, 복수 세목·주체, 일반 문장 인용, 잘못된 Judge ID, 의존 주장 차단, 미검증 SSE 전송 방지를 포함한다. 최종 실행 결과는 CURRENT_STATUS.md를 따른다.

# 로드맵 — 평가 지표·성능 개선·배포

정리일: 2026-11-06. **이 문서는 앞으로의 계획이며 구현 완료 기록이 아니다.**
수치의 원본은 [CURRENT_STATUS.md](CURRENT_STATUS.md), 설계 결정은 [DECISIONS.md](DECISIONS.md), 당장 할 일과 결과 위치는
[HANDOFF.md](HANDOFF.md)의 "현재 인계"다. Reranker의 상세 설계는 [RAG_IMPROVEMENT_PLAN.md](RAG_IMPROVEMENT_PLAN.md)를 따른다.

## 원칙

- **지표 먼저, 개선은 하나씩.** 바꾸기 전에 같은 문항·같은 방식으로 기준값을 재고, 바꾼 뒤 같은 지표로 비교해 나아졌을 때만 반영한다.
  벡터 검색만으로는 나았던 임베딩 모델이 실제 검색 경로에서는 나아지지 않은 사례가 있다(ADR-079).
- **조정과 판정을 나눈다.** 평가 문항을 개발용(설정 조정에 사용)과 시험용(채택 판정에만 사용)으로 나누고, 시험용으로는 조정하지 않는다.
- **차이는 문항 단위로 본다.** 평균 점수와 함께 "한쪽만 맞힌 문항 수"와 부호 검정 p값을 기록한다(`evaluation/embedding_candidate.py compare`).
  203문항 규모에서는 대략 4~5%p 미만의 차이를 우연과 구분하기 어렵다.
- **유료 호출은 최소로.** 실제 모델을 부르는 평가는 호출 수와 질문 수를 먼저 밝히고, 코드·저장 결과로 확인할 수 있는 것은 무료로 확인한다(AGENTS.md).
- **기록 위치를 지킨다.** 실험 산출물은 `evaluation/runs/`(Git 제외), 결과 수치는 CURRENT_STATUS, 채택·기각 이유는 DECISIONS에 남긴다.

## 트랙 A — 평가 지표

| # | 작업 | 방법 | 비용 |
|---|---|---|---|
| A1 | 검색 평가셋 개발·시험 분리 | `build_embedding_set.py`에 `split`을 더해 묶음(일상·해석례·기존)별로 약 6:4로 나눈다. 같은 조문을 정답으로 하는 문항은 같은 쪽에 둔다. 시험용은 채택 판정에만 쓴다 | 없음 |
| A2 | 라벨 검수·오답 후보 | 50문항 이상을 공식 원문과 대조해 `review` 상태를 남긴다. 헷갈리는 오답(법↔시행령, 인접 번호, 다른 세목의 같은 용어)을 `hard_negatives`로 더한다 | 없음 |
| A3 | 파이프라인 검색 지표 | 질문 계획을 거친 쟁점별 필수 조문 회수율(`evaluation/issue_retrieval_probe.py`). 평가셋 문항은 계획 없이 원문 하나로 검색하므로 실제 답변 경로와 차이가 있다 | 질문당 계획 호출 1회 |
| A4 | 답변 정답 기준 세트 | 30~50문항. 문항마다 반드시 들어갈 결론·요점, 근거 조문, 들어가면 안 되는 주장, 보류해야 하는지를 적는다. 6개 세목과 유형(요건·계산·절차·과거 사건·범위 밖)을 고르게 섞는다 | 없음(작성) |
| A5 | 답변 지표 | 요점 포함률, 주장별 근거 일치율(기존 주장 검사), 틀린 결론 비율, 보류·거절의 적절성, 계산 정확도. Judge 채점 20건을 사람이 다시 채점해 일치율을 함께 기록하고, Judge는 생성 모델과 다른 계열을 쓴다 | 문항당 6~10회 호출 |
| A6 | 운영 지표 | 단계별 시간 중앙값·95분위, 답변 1건 비용, 시간 초과·실패율, 차단율, 보완 라운드 발생률. 출처는 `LLM call` 로그와 `chat_usage` | 실측 때만 |
| A7 | 반복 실행 | 검색 평가(무료, DB 필요)를 명령 하나로 돌리고 직전 기준과 비교표를 만든다. CI에는 DB가 없으므로 오프라인 계약·데이터셋 검증만 둔다 | 없음 |

**변경 채택 기준(초안)** — 시험용 문항에서:

- 검색: 전체 hit@5가 떨어지지 않고(한쪽만 맞힌 문항 기준 p ≥ 0.05인 하락도 원인 확인), 목표 지표(예: 일상 표현 hit@1)가 오른다.
- 답변: 요점 포함률과 근거 일치율이 떨어지지 않고, 틀린 결론이 늘지 않는다.
- 운영: 답변 시간 95분위가 10% 넘게 늘지 않고, 1건 비용이 늘면 그만큼의 품질 개선이 있다.

## 트랙 D — 배포

| 단계 | 구성 | 할 일 | 넘어가는 조건 |
|---|---|---|---|
| **D1 (지금)** | Vercel(화면) + 이 PC(백엔드, Tailscale Funnel) | Tailscale 로그인 → MagicDNS·HTTPS 인증서 켜기 → `tailscale funnel --bg 3001` → `vercel.json`의 백엔드 주소 반영·푸시 → Vercel 프로젝트 연결(루트 `frontend`) → 외부에서 체험 계정·긴 답변(heartbeat)·업로드(4MB) 확인. 운영: Docker·Ollama·Tailscale 자동 시작, 절전 해제, 백업 외부 복사, 무료 가동 감시 | 상시 가동이 필요하거나 PC 부담이 클 때 D2 |

| D3 | 관리형 DB + 컨테이너 호스팅 | 사용량·비용을 보고 정한다 | — |

단계마다 확인: 비밀값이 이미지·저장소에 없음(`.dockerignore`, `scripts/check_secrets.py`), 하루 질문 한도, 쿠키 Secure, 로그·추적에

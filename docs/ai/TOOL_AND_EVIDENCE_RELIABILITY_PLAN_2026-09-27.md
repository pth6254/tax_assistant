# 도구 선택과 근거 채택 신뢰성 개선안

작성: 2026-09-27. 범위: 코드 검토, 외부 기술 자료 조사, 합성 입력 재현 및 구현 제안. 이번 조사에서는 서비스 코드·DB·실행 컨테이너를 변경하지 않았다.

## 1. 확인한 문제

| 경계 | 현재 동작과 근거 | 발생 가능한 문제 | 확인 수준 |
|---|---|---|---|
| 질문 → 도구 | `tools/planner.py`의 단어 판별 후 LLM이 모든 등록 도구 중 하나를 선택한다. 입력 스키마 검증은 있으나 질문이 그 도구 사용을 요구했는지 검증하는 단계는 부족하다. | 설명 질문을 계산/원문/사용자 문서 조회로 오분류 | 코드 확인, 세금계산서 사례는 이전 작업에서 재현·수정 |
| 도구 없음 → 처리 | `select_tool`의 `none`을 `run_tools_for_query`가 `needs_input`으로 바꾼다. | 도구가 불필요한 질문까지 입력 부족으로 중단 | 코드 확인 |
| 복합 질문 → 검색 범위 | `chat_service._classify_and_generate_queries`는 복수 세목을 감지해도 LLM의 단일 `law` 값으로 최종 필터를 좁힐 수 있다. | 법인세·부가가치세 중 한쪽 근거 누락 | 합성 모델 출력으로 재현 |
| 문서 → 공식 출처 | `format_hybrid_context`가 문서 본문을 그대로 붙이고, `citation_guard`가 문자열의 `[출처: ...]` 표식을 다시 분석한다. | 업로드 본문의 위조 표식이 공식 법령 근거로 인정될 수 있음 | 합성 사용자 문서로 재현 |
| 자료 유형 → 권위 | 업로드 문서도 category에 따라 `source_type=law/regulation/rule`로 표시될 수 있다. | 법령을 다루는 업로드 자료와 공식 수집 원문의 권위를 혼동 | 코드 확인. 이것만으로 citation guard가 통과한다는 뜻은 아님 |
| 검색 → 사건 적용 | 일반 검색 SQL은 `is_current`를 사용하고 `HybridSearchResult`에는 시행일·원본 ID·버전·원문 hash 필드가 없다. | 현행 원문이 사건 시점에 적합한지, 원문과 색인이 같은 버전인지 추적하기 어려움 | 코드 확인. 과거법령 별도 경로의 기존 보호 장치는 존재 |
| 검색 점수 → 근거 충분성 | 벡터 유사도 임계값과 법령 우선순위를 적용하고, 상위 3개 평균 유사도로 웹 보충 여부를 정한다. | 비슷한 표현의 조문을 확보해도 필수 쟁점·예외·주체의 근거가 빠질 수 있음 | 코드상 위험. 실제 오답률은 미측정 |
| 인용 → 결론 | `verify_citations`는 조문/하위 단위의 존재를 확인한다. 계산 검사는 마지막 금액 문자열의 포함 여부다. | 실제 있는 조문을 잘못 해석하거나 올바른 숫자를 잘못된 의미로 사용해도 통과 가능 | 검사 범위 확인 |
| 단일 조회 실패 → 전체 답변 | 명시적 조회 도구의 실패는 일반 검색을 우회하고 최종 설명도 보류한다. | 복합 요청의 보조 조회 실패가 답변 전체를 막음 | 코드 확인 |

기존 사용자 문서 소유자 필터, 도구 허용 목록, 인자 스키마, 조회 시간 제한, 과거법령 버전 검사, 그래프 원문 재대조는 유지할 보호 장치다. 아래 제안은 그 위에 필요한 경계를 추가한다.

### 읽기 전용 합성 재현

WSL 가상환경에서 DB 접근과 외부 모델 호출 없이 실행했다. 분류 모델은 AsyncMock으로 대체하고 LangSmith tracing을 비활성화했다.

1. 질문에 법인세·부가가치세를 함께 넣고 분류 결과를 법인세법 하나로 고정했다. 키워드 감지 개수는 2였지만 최종 검색 필터는 ALL이 아니었다.
2. `source_type=user_pdf`, `category=기타`인 합성 문서 본문에 가상의 법령명과 공식 출처 형식 표식을 넣었다. 컨텍스트 포맷 이후 그 가상 법령 인용을 검사했을 때 verified가 참이었다.

결과:

```json
{"detected_law_count":2,"multi_law_narrowed_to_one":true,"forged_user_document_marker_accepted":true}
```

이는 함수 경계의 취약 동작 재현이다. 실제 사용자 문서가 오염됐거나 모든 실제 생성 답변에서 이 문제가 발생했다는 의미는 아니다.

## 2. 권장 처리 구조

질문을 작업으로 나누기 → 허용 도구/입력 출처 검사 → 도구 실행과 쟁점별 검색 → 근거 원본/버전 확인 → 주장별 초안 → 코드 검사와 의미 검사 → 검사를 통과한 범위의 답변 전달.

라우팅과 작업 분해를 명시적 workflow로 구성하는 방식은 [Anthropic의 workflow 설명](https://www.anthropic.com/engineering/building-effective-agents)에 근거한다. 여기서는 새로운 에이전트 프레임워크를 도입하기보다 기존 Python 오케스트레이션에 검사 단계를 추가하는 것을 제안한다.

### A. 질문을 작업으로 나누고 실행 전에 검사한다

모델은 `analysis`, `exact_lookup`, `document_search`, `calculation` 작업과 필요한 입력을 제안한다. `no_tool_needed`, `needs_input`, `unsupported`, `selection_error`를 각각 구분한다. 문장 속 단어는 실행을 강제하는 조건으로 사용하지 않는다.

각 작업은 다음 정보를 가져야 한다.

- 원 질문의 어떤 요청을 처리하는지: issue ID, 질문의 실제 발췌 위치.
- 처리 대상: 주체, 세목/법령 후보 목록, 사건일·과세기간, 명시된 가정.
- 필요한 정보와 부족한 정보, 선행 작업, 사용 가능한 출처 종류.
- 계산 입력별 출처: 사용자 발언 또는 확인된 문서 값. 모델이 작성한 이전 답변은 확정 입력으로 승격하지 않는다.

서버는 도구별 조건을 검사한다.

| 작업 | 실행 조건 | 조건 미충족 시 |
|---|---|---|
| 특정 조문 원문 조회 | 명시적 원문 요청과 식별 가능한 법령·참조. 맥락 보완은 실제 이전 사용자 입력에 연결 | 일반 설명이면 검색, 원문 요청인데 식별 불가하면 필요한 법령/참조를 질문 |
| 사용자 문서 검색 | 문서 조회 요청, 서버가 확인한 소유권과 문서 범위 | 문서 미지정/미업로드를 구체적으로 안내. 공개 법령을 사용자 문서 결과로 대체하지 않음 |
| 세액 계산 | 지원 세목, 산출 요청, 필수 입력·단위·출처 확인 | 누락 입력을 질문. 없는 법인세 계산기를 다른 계산기로 대체하지 않음 |
| 일반 세무 분석 | 쟁점별 검색 계획과 필요한 근거 종류 | 근거 부족 쟁점을 재검색하거나 추가 조건을 질문 |

복합 요청은 여러 작업을 묶되 호출 수·시간·재검색 횟수를 제한한다. 모델의 자기평가 confidence 점수만으로 실행을 허용하지 않는다.

### B. 근거의 출처는 서버 데이터로 결정한다

생성 모델과 Judge에 전달할 근거를 구조화 객체로 유지한다. 제안 필드는 `evidence_id`, `origin_kind`, `source_id`, `document_id`, `version_id`, `law_name`, `reference`, `effective_from`, `effective_to`, `collected_at`, `content_hash`, `quote`, `location`, `retrieval_status`다. 소유권과 수집 경로는 서버가 설정한다.

- 공식 수집 원문, 사용자 업로드, 공식 웹 원문, 검색 스니펫을 구분한다. 업로드 파일이 법령을 다뤄도 출처는 사용자 업로드다.
- 인용 검사는 문자열의 출처 표식을 파싱하지 않고 서버가 만든 evidence ID로 원본을 조회한다. ID 존재, 원문 hash, 버전, 정확한 발췌 범위를 검사한다.
- 프롬프트용 문자열은 구조화 근거에서 파생한 표시 형식이다. 본문 안의 표식·지시·URL로 신뢰 등급을 변경할 수 없다.
- 수집 시 공식 원본 식별자·버전·수집 시각·무결성 정보를 남기고 파싱 누락/실패는 격리한다. hash 일치는 원본 유지 여부만 보여주며 법적 해석의 정확성은 별도다.
- 웹 검색 스니펫은 발견용으로 사용한다. 결론에 채택하려면 공식 원문을 확보하고 문서 날짜·대상·발췌 범위를 확인한다. 확보하지 못하면 확인된 법적 근거로 승격하지 않는다.

### C. 검색을 쟁점별로 수행하고 누락을 확인한다

복수 세목을 단일 `law`로 축소하지 않는다. 주체×세목×쟁점별로 질문과 검색 범위를 만들고 필수 근거의 존재를 확인한다. 전체 검색의 상위 몇 건을 확보한 것만으로 충분하다고 판단하지 않는다.

사용자가 제시한 컨설팅 사례에서는 최소한 사실확인 자료, H회사 법인세, H회사 부가가치세, I회사 법인세, I회사 부가가치세를 답변 요구사항으로 유지한다. 이는 검색 분해 예시이며 각 항목의 세무 결론을 미리 정하는 것이 아니다.

- 관련성 확인 후 원문의 권위·시점·적용 대상을 고려해 채택한다. 법률이라는 이유로 질문과 무관한 조문을 앞세우지 않는다.
- 사건일이 필요한 결론은 그 날짜를 확인한다. 시행일만으로 경과규정과 적용례가 해결됐다고 판단하지 않는다.
- 질문한 항·호·목과 조 전체를 구분하고 누락/모호성 상태를 전달한다.
- 근거가 부족하면 해당 쟁점만 제한된 횟수로 재검색한다. 검색어 확대가 법령명·연도·납세자 범위 조건을 지우지 않도록 검사한다.
- 임베딩은 기존 Ollama를 유지한다. 재정렬 모델의 추가나 검색 방식 교체는 쟁점별 근거 회수율을 실제 평가해 결정한다.

### D. 주장 단위로 의미를 확인한다

답변 초안은 주장별 evidence ID, 원문 발췌, 적용 주체, 조건, 시점, 의존하는 주장 ID를 포함하게 한다. 모델이 적은 설명 이유 자체를 검증 증거로 인정하지 않는다.

코드는 도구 인자와 사용자 입력의 일치, evidence ID·발췌·버전·소유권, 계산식/입력/결과 연결을 검사한다. LLM Judge는 근거가 주장을 지지하는지, 반대 조건·예외를 빠뜨렸는지, 질문의 필수 쟁점을 다뤘는지 평가한다. Judge 출력은 `supported`, `contradicted`, `insufficient`와 근거 ID/발췌를 포함한다.

검색 문서 대비 답변의 충실성과 독립 정답 대비 정확도는 구분해서 평가해야 한다. [LangSmith 공식 RAG 평가 안내](https://docs.langchain.com/langsmith/evaluate-rag-tutorial)는 correctness, groundedness, relevance, retrieval relevance를 각각 측정한다. [ALCE 연구](https://arxiv.org/abs/2305.14627)도 답변 정확성과 인용 품질을 별도로 다룬다.

기존 `evaluation/judge.py`를 운영 평가에 확장한다. 생성은 OpenRouter GPT-6 Luna, 임베딩은 Ollama를 유지한다. 동일 모델 Judge의 편향 가능성을 기록하고 전문가가 판정한 오답/정답으로 잘못된 통과와 과도한 보류를 측정한다. 다른 모델을 쓰는 것만으로 독립적인 정답이 생기지는 않는다.

온라인 Judge 도입은 별도 기능 플래그와 관측 모드로 시작한다. 교정 전 점수는 서비스 답변 통과를 보증하지 않는다. 평가셋의 독립 정답을 실제 답변 생성 컨텍스트에 섞지 않는다.

### E. 실패의 영향을 의존하는 결론에 한정한다

실패 종류를 `missing_input`, `not_found`, `not_collected`, `version_mismatch`, `source_untrusted`, `timeout`, `unsupported_claim` 등으로 기록한다. 조회 실패를 규정 부존재로 번역하지 않는다.

보조 조회 실패 후에도 독립적으로 확인된 쟁점은 설명할 수 있다. 실패한 전제에 의존하는 계산·비교·최종 추천은 함께 보류한다. 단순히 실패한 문장만 삭제하고 그것에 의존한 결론을 남겨서는 안 된다. 명시적 사용자 문서 조회 실패를 일반 법령 설명으로 조용히 대체하지 않는다.

화면에는 쟁점별 답변 가능 여부, 확인한 근거, 추가 조건과 보류 사유를 표시한다. 내부 raw confidence 점수를 세무 정확도처럼 보여주지 않는다.

## 3. LangSmith에서 확인할 평가

운영 평가는 사용자의 결정대로 LangSmith를 사용한다. 로컬에는 재현 가능한 평가 입력·결과를 보존하고 전송 실패가 채팅 답변의 통과 여부를 바꾸지 않게 한다.

| 단계 | 핵심 지표/검사 |
|---|---|
| 계획 | 질문 유형별 잘못된 도구 실행률, 불필요 실행률, 도구 필요 요청의 누락률 |
| 입력 | 계산 입력의 사용자/문서 출처 일치, 누락/0 구분, 지원하지 않는 작업 거절 |
| 출처 | 타인 문서·위조 표식·미검수 자료·다른 버전의 채택 차단 |
| 검색 | 쟁점별 필수 근거 회수율, 관련 없는 근거 비율, 주체/연도 혼동 |
| 답변 | 주장별 근거 지지, 모순, 필수 쟁점과 예외 누락 |
| Judge | 전문가 골드 대비 오답 통과율, 정답 차단율, unknown/error 비율 |
| 사용자 경험 | 유효한 답변 제공률, 부분 답변률, 불필요 보류율, 지연·호출 비용 |

질문과 지문에서 `계산/계산서`, 금액/연도, `문서` 언급/실제 문서 검색 요청, 현행/과거, 단일/복합 세목, 정상/누락 입력을 교차한 사례를 만든다. 사용자 문서의 가짜 공식 출처 표식, 동일 조문 번호의 다른 법령·버전, 잘못된 인용과 무관한 올바른 조문도 포함한다. 일부 실패가 전체 요청을 중단시키는지와 실패한 전제에서 결론을 이어가는지도 검사한다.

튜닝 사례와 최종 평가 사례는 분리한다. 권한·원본 ID·버전 등 코드로 보장할 규칙은 회귀 사례 전부 통과를 요구한다. 의미 정확도와 답변 제공률은 전문가 골드의 표본 수·오류율·불확실성을 함께 보고 배포 기준을 정한다. 모든 질문을 보류해서 낮은 오답률을 만드는 방식을 성공으로 평가하지 않는다.

## 4. 구현 우선순위

1. **즉시 보강:** 공식 근거 검사에 구조화 출처 사용, 복수 세목 필터 보존, `no_tool_needed`/입력 부족 구분, 선택/거절 사유와 안전한 도구 인자 기록.
2. **처리 흐름 확장:** 질문의 작업 분해, 도구 사용 조건과 입력 출처 검사, 쟁점별 검색·근거 충족 확인, 실패 의존성에 따른 부분 답변.
3. **의미 검증 교정:** 독립 전문가 골드와 기존 Judge를 연결하고 LangSmith에서 오류 유형별 비교. 관측 결과와 지연·비용을 확인한 뒤 온라인 적용 범위 결정.

우선 수정 대상: `app/services/tools/planner.py`, `app/schemas/tool_call.py`, `app/services/chat_service.py`, `app/schemas/law.py`, `app/services/search/hybrid_search_service.py`, `app/services/citation_guard.py`, `app/services/answer_verification.py`, `evaluation/`.

복잡한 프레임워크 추가나 생성/임베딩 모델 교체는 선행 조건이 아니다. 먼저 잘못된 도구 실행과 잘못된 출처 승격을 코드로 차단하고, 검색과 의미 검증 개선은 평가로 확인한다. 이 구조도 모든 세무 오답의 부재를 보장하지 않으며 현재 발견된 오류 경로를 차단하고 남은 오류를 측정하기 위한 설계다.
